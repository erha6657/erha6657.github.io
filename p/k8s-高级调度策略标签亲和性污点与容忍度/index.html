目标与应用场景

核心知识目标

  1. 理解 Kubernetes 中标签（Label）的基本概念，掌握标签的创建、查看和删除操作，能够使用标签对 Pod 资源进行分组管理。
  2. 掌握 Node 节点选择器的使用方法，包括 nodeName 和 nodeSelector 两种方式，能够将 Pod 调度到指定的 Node 节点。
  3. 深入理解 Node 节点亲和性（nodeAffinity）的原理和配置方法，能够使用硬亲和性和软亲和性控制 Pod 调度。
  4. 掌握 Pod 亲和性（podAffinity）和 Pod 反亲和性（podAntiAffinity）的配置方法，理解拓扑键（topologyKey）的使用场景。
  5. 理解污点（Taints）和容忍度（Tolerations）的工作机制，能够合理配置污点和容忍度实现生产环境与测试环境的隔离。
  6. 掌握 Pod 常见状态（Pending、Running、Failed 等）的含义和排查方法，理解三种重启策略（Always、OnFailure、Never）的区别。

典型应用场景

  • 场景一：生产环境与测试环境隔离 在企业级 Kubernetes 集群中，通常需要在同一集群中同时运行生产环境和测试环境的应用。通过在生产环境节点上添加污点，并配置生产环境 Pod 的容忍度，可以确保只有具有相应容忍度的 Pod 才能被调度到生产节点，从而实现环境的逻辑隔离，避免测试流量影响生产服务。

  • 场景二：关键服务节点亲和部署 对于需要低延迟通信的服务（如 Web 服务器与缓存服务），可以使用 Pod 亲和性（podAffinity）将它们调度到同一个节点或同一机架的节点上，减少网络通信开销。同时，对于同一服务的多个副本，可以使用反亲和性（podAntiAffinity）将它们分散到不同节点，避免单点故障。

  • 场景三：特殊硬件节点调度 当集群中存在具有特殊硬件（如 GPU、SSD、大内存）的节点时，可以为这些节点打上特定的标签，并使用节点亲和性（nodeAffinity）将需要这些硬件资源的工作负载调度到相应节点，实现硬件资源的高效利用。

节点选择基础：nodeName 与 nodeSelector

nodeName 方式

nodeName 是最简单的节点指定方式。直接在 Pod 的 spec 字段中指定 nodeName 值为目标 Node 节点的名称，Pod 就会跳过调度器直接运行在指定的节点上。这种方式适用于需要将 Pod 固定运行在特定节点的场景。

apiVersion: v1                    # 使用Kubernetes核心API版本v1
kind: Pod                         # 资源类型声明为Pod
metadata:
  name: demo-pod                  # Pod名称，在命名空间内唯一
  namespace: default              # Pod所属命名空间（默认命名空间）
  labels:                         # Pod标签（键值对，用于资源筛选/关联）
    app: myapp                    # 标识应用名称
    env: dev                      # 标识环境类型（开发环境）
spec:
  nodeName: node1                 # 指定Pod调度到名为node1的节点上（强制调度）
  containers:                     # Pod内的容器列表
  - name: tomcat-pod-java         # 容器名称（Pod内唯一）
    image: tomcat:8.5-jre8-alpine # 容器镜像（轻量级Alpine版本的Tomcat 8.5）
    imagePullPolicy: IfNotPresent # 镜像拉取策略：本地有则用本地，无则拉取
    ports:                        # 容器暴露的端口
    - containerPort: 8080         # 容器内Tomcat服务的端口（仅声明，不暴露到集群外）

注意： 这里的 node1 指的是主机名称，可以通过 hostnamectl set-hostname node1 命令进行设置。使用 kubectl get pods -o wide 可以查看 Pod 被调度到了哪个节点。如果指定的 nodeName 节点不存在或不可用，Pod 将保持 Pending 状态无法成功运行。

nodeSelector 方式

nodeSelector 允许通过标签选择节点。首先需要为目标节点打上标签，然后在 Pod 配置中通过 nodeSelector 字段指定需要匹配的标签条件。只有拥有所有指定标签的节点才会被考虑进行调度。

kind: Pod                         # 资源类型声明为Pod
metadata:
  name: demo-pod-1                # Pod名称，在命名空间内唯一

    disk: test                    # 仅调度到带有"disk: test"标签的节点上
  containers:                     # Pod内的容器列表
  - name: tomcat-pod-java         # 容器名称（Pod内唯一）
    image: tomcat:8.5-jre8-alpine # 容器镜像（轻量级Alpine版本的Tomcat 8.5）
    imagePullPolicy: IfNotPresent # 镜像拉取策略：本地有则用本地，无则拉取

    - containerPort: 8080         # 容器内Tomcat服务的端口（仅声明，不暴露到集群外）

注意： 如果同时使用 nodeName 和 nodeSelector，两个条件都必须满足，否则 Pod 调度会失败。删除节点标签可以使用 kubectl label nodes <node-name> <label-key>-（标签键后加短横线）。

标签（Label）管理

标签（Label）是 Kubernetes 中一种轻量级的分类机制，它是一对键值对（Key/Value），被关联到 Kubernetes 对象上（如 Pod、Node、Service 等）。标签允许用户以灵活、多维的方式组织和管理集群资源。每个对象可以拥有多个标签，但同一个对象的标签键必须唯一。

常用标签操作命令

添加标签

添加标签的语法为 kubectl label <资源类型> <资源名称> <key>=<value>。

节点亲和性（Node Affinity）

节点亲和性（nodeAffinity）用于基于 Node 节点的标签来定义调度规则。相比于 nodeSelector，它提供了更丰富的匹配操作符以及硬亲和性与软亲和性的区分。

硬亲和性（Required）

requiredDuringSchedulingIgnoredDuringExecution 规定了在调度时必须满足的条件，如果不满足条件，Pod 将保持 Pending 状态。

apiVersion: v1  # API 版本，指定使用 Kubernetes 核心 API 的 v1 版本
kind: Pod       # 资源类型，声明这是一个 Pod 类型的 Kubernetes 资源
metadata:       # 元数据部分，包含资源的标识信息和附加属性
  name: pod-node-affinity-demo  # Pod 名称，在同一命名空间内必须唯一，用于唯一标识该资源
  namespace: default            # 所属命名空间，将 Pod 部署到 default 命名空间（默认命名空间）
  labels:                       # 标签配置，用于对资源进行分类、筛选和管理
    app: myapp                  # 标签键值对，标识该 Pod 属于 myapp 应用
    tier: frontend              # 标签键值对，标识该 Pod 属于前端服务层级
spec:           # 规格配置，定义 Pod 的详细规格、运行参数和期望状态
  affinity:     # 亲和性配置，控制 Pod 的调度位置策略（节点亲和性、Pod亲和性等）
    nodeAffinity:  # 节点亲和性配置，基于节点标签来控制 Pod 调度到哪些节点
      requiredDuringSchedulingIgnoredDuringExecution:  # 硬亲和性策略：调度时必须满足条件，否则 Pod 保持 Pending 状态
        nodeSelectorTerms:  # 节点选择器条目列表（多个条目为逻辑 OR 关系）
        - matchExpressions:  # 匹配表达式配置，基于标签键值对进行条件匹配
          - key: zone        # 要匹配的标签键名：查找具有 zone 标签的节点
            operator: In     # 操作符类型：In 表示标签值必须在指定的 values 列表中
            values:          # 允许的标签值列表（满足任一值即可匹配成功）
            - foo            # 允许值1：节点标签为 zone=foo 时满足调度条件
            - bar            # 允许值2：节点标签为 zone=bar 时满足调度条件
  containers:    # 容器列表，定义 Pod 中包含的一个或多个容器
  - name: myapp  # 容器名称（同一 Pod 内唯一），用于标识不同容器
    image: docker.io/ikubernetes/myapp:v1  # 容器镜像地址：从 Docker Hub 拉取 ikubernetes/myapp:v1 镜像
    imagePullPolicy: IfNotPresent          # 镜像拉取策略：IfNotPresent 表示本地已有镜像时不重复拉取

匹配操作符说明：

  • In：键值在列表中。
  • NotIn：键值不在列表中。
  • Exists：指定的键存在。
  • DoesNotExist：指定的键不存在。
  • Gt：大于。
  • Lt：小于。

软亲和性（Preferred）

preferredDuringSchedulingIgnoredDuringExecution 定义了调度的偏好条件。系统会尽量满足条件，但如果不满足，Pod 仍然能调度到其他节点。可以通过权重（weight）来控制多个偏好条件的优先级。

affinity:                       # 亲和性配置：控制Pod调度策略
  nodeAffinity:                 # 节点亲和性配置
    # 软亲和性策略：优先满足条件，不满足也可调度（非强制）
    preferredDuringSchedulingIgnoredDuringExecution:
    - preference:               # 第一个偏好条件（权重10）
        matchExpressions:       # 标签匹配表达式
        - key: zone1            # 匹配节点标签键：zone1
          operator: In          # 匹配规则：标签值需在values列表中
          values:               # 允许的标签值列表
            - foo1              # 允许值1：zone1=foo1
            - bar1              # 允许值2：zone1=bar1
      weight: 10                # 权重：10（权重越高，优先级越高）
    - preference:               # 第二个偏好条件（权重20）
        matchExpressions:       # 标签匹配表达式
        - key: zone2            # 匹配节点标签键：zone2
          operator: In          # 匹配规则：标签值需在values列表中
          values:               # 允许的标签值列表
            - foo2              # 允许值1：zone2=foo2
            - bar2              # 允许值2：zone2=bar2
      weight: 20                # 权重：20（此条件优先级高于第一个）

工作机制： 软亲和性的权重会在调度预选到优选（Priorities）的过程中，在原有节点打分的基础上加分，从而挑选得分最高的节点进行调度。

Pod 亲和性与反亲和性

Pod 亲和性与反亲和性控制的是 Pod 之间的相对部署关系，例如让相关的 Pod 尽量部署在同一拓扑域中（亲和），或者将相同的 Pod 分散在不同节点以提升可用性（反亲和）。

Pod 亲和性（Pod Affinity）

Pod 亲和性用于将相关的 Pod 部署在同一位置（如同一个节点、同一可用区、同一机架等）。拓扑键（topologyKey）定义了位置匹配的范围（例如 kubernetes.io/hostname 表示以节点为拓扑域）。

apiVersion: v1                    # 使用Kubernetes核心API版本v1
kind: Pod                         # 资源类型声明为Pod
metadata:
  name: pod-second                # Pod名称，命名空间内唯一
  labels:                         # Pod标签，用于亲和性匹配/资源筛选
    app: backend                  # 标识应用类型为后端服务
    tier: db                      # 标识服务层级为数据库层
spec:
  affinity:                       # 亲和性配置：控制Pod间的调度关系
    podAffinity:                  # Pod亲和性配置（强制调度到指定Pod同节点）
      # 硬亲和性策略：调度时必须满足条件，否则Pod保持Pending状态
      requiredDuringSchedulingIgnoredDuringExecution:
      - labelSelector:            # 标签选择器：匹配目标Pod的标签
          matchExpressions:       # 匹配表达式（精准匹配标签规则）
          - key: app2             # 要匹配的目标Pod标签键
            operator: In          # 操作符：标签值需在values列表中
            values: ["myapp2"]    # 目标Pod的标签值需为myapp2
        topologyKey: kubernetes.io/hostname  # 拓扑域：匹配到同一主机（节点）
  containers:                     # Pod内的容器列表
  - name: busybox                 # 容器名称（Pod内唯一）
    image: busybox:latest         # 容器镜像：最新版busybox
    imagePullPolicy: IfNotPresent # 镜像拉取策略：本地有则用本地，无则拉取
    command: ["sh","-c","sleep 3600"]  # 容器启动命令：休眠3600秒（持续运行）

apiVersion: v1                    # 使用Kubernetes核心API版本v1
kind: Pod                         # 资源类型声明为Pod
metadata:
  name: pod-second                # Pod名称，命名空间内唯一
  labels:                         # Pod标签，用于资源筛选/关联
    app: backend                  # 标识应用类型为后端服务
    tier: db                      # 标识服务层级为数据库层
spec:
  affinity:                       # 亲和性配置：控制Pod间的调度关系
    podAntiAffinity:              # Pod反亲和性配置（强制不调度到指定Pod同节点）
      # 硬反亲和性策略：调度时必须满足条件，否则Pod保持Pending状态
      requiredDuringSchedulingIgnoredDuringExecution:

污点（Taints）与容忍度（Tolerations）

与节点亲和性（让 Pod 倾向于调度到特定 Node）相反，污点（Taints）和容忍度（Tolerations）是一种排斥机制：污点定义在节点上，使节点能排斥特定的 Pod；而容忍度则定义在 Pod 上，使 Pod 能够被调度到带有特定污点的节点上。

污点的概念与效果

污点可以通过以下命令添加： kubectl taint node <node-name> <key>=<value>:<effect>

Kubernetes 提供以下三种效果：

  • NoSchedule：新 Pod 如果不能容忍该污点，则无法调度到该节点。已在该节点运行的 Pod 不受影响。
  • PreferNoSchedule：系统会尽量避免将未容忍污点的 Pod 调度到该节点，但不保证绝对排斥（属于软排斥）。
  • NoExecute：不仅影响调度过程，还会影响已运行在节点上的 Pod。如果不容忍新添加的污点，已运行的 Pod 会立即被驱逐。

# 格式：kubectl taint nodes <节点名> <污点键>=<污点值>:<污点效果>
# 示例1：添加「禁止无容忍度的Pod调度」的污点（最常用）
kubectl taint nodes k8s-node-01 node-type=production:NoSchedule

# 示例2：添加「禁止无容忍度的Pod调度，且驱逐已有无容忍度的Pod」的污点
kubectl taint nodes k8s-node-02 node-type=production:NoExecute

# 示例3：添加「优先不调度无容忍度的Pod」的软污点（非强制）
kubectl taint nodes k8s-node-03 node-type=production:PreferNoSchedule

# 删除特定污点 (格式：kubectl taint nodes <节点名> <污点键>-)
kubectl taint nodes k8s-node-01 node-type-

# 清空所有污点（会删除该节点的所有污点配置）
kubectl taint nodes k8s-node-01 --all-taints-

apiVersion: v1  # API 版本，指定使用 Kubernetes 核心 API 的 v1 版本
kind: Pod       # 资源类型，声明这是一个 Pod 类型的 Kubernetes 资源对象
metadata:       # 元数据部分，包含资源的标识信息和附加属性

spec:           # 规格配置，定义 Pod 的详细规格、运行参数和期望状态
  containers:   # 容器列表，定义 Pod 中包含的一个或多个容器
  - name: myapp # 容器名称，在同一 Pod 内必须唯一，用于标识不同容器
    image: ikubernetes/myapp:v1  # 容器镜像地址，从仓库拉取 ikubernetes/myapp:v1 镜像
    imagePullPolicy: IfNotPresent # 镜像拉取策略，IfNotPresent 表示本地已有镜像时不重复拉取
    ports:      # 端口配置列表，定义容器对外暴露的网络端口
    - name: http # 端口名称，用于标识该端口的用途（如 HTTP 服务）
      containerPort: 80 # 容器内部端口号，容器进程监听的端口
  tolerations:  # 容忍度列表，定义 Pod 能够容忍节点上的哪些污点
  - key: "node-type"    # 污点键名，与节点上定义的污点键名匹配才能生效
    operator: "Equal"   # 操作符，Equal 表示需要完全匹配污点的 key 和 value
    value: "production" # 污点值，与节点上定义的污点值必须相等才会接受
    effect: "NoSchedule" # 污点效果，NoSchedule 表示不容忍此污点的 Pod 不会被调度到该节点

对于 NoExecute 效果的污点，还可以在容忍度配置中加入 tolerationSeconds，用以定义 Pod 在被驱逐前可以容忍该污点的最长时间。

      - preference:               # 第二个偏好条件（权重20）
          matchExpressions:       # 标签匹配表达式
          - key: zone2            # 匹配节点标签键：zone2

Prometheus 监控系统从入门到进阶

Prometheus 是一个开源的云原生监控系统，最初由 SoundCloud 开发，现在已成为继 Kubernetes 之后第二个从云原生计算基金会（CNCF）毕业的项目。它的核心设计目标是实现高可靠性和易用性，尤其适合在动态的微服务架构中进行监控。Prometheus 采用独特的 “拉取”（Pull）模型，定期从配置好的目标（如应用程序、服务器）上抓取指标数据，并将其存储在内置的时序数据库中。它还提供了一个强大的查询语言 PromQL，允许用户灵活地查询和聚合这些监控数据，并结合 Alertmanager 组件实现灵活的警报机制。

Prometheus 以时间序列数据的形式收集和存储其指标，即指标信息与其记录时的时间戳一起存储，以及称为标签的可选键值对。

官网：https://prometheus.io/

特性

Prometheus 的主要特性包括：

  • 一个多维数据模型，时间序列数据由指标名称和键/值对标识
  • PromQL，一种灵活的查询语言，以利用这种维度
  • 不依赖分布式存储；单个服务器节点是自治的
  • 时间序列数据通过 HTTP 拉取模型进行采集
  • 通过中间网关支持推送时间序列
  • 通过服务发现或静态配置发现目标
  • 多种图形和仪表盘支持模式

什么是指标

通俗地说，指标是数值测量。术语“时间序列”指的是记录随时间的变化。用户想要测量的东西因应用程序而异。对于 Web 服务器，它可能是请求时间；对于数据库，它可能是活动连接数或活动查询数，等等。

指标在理解您的应用程序为何以某种方式工作方面发挥着重要作用。假设您正在运行一个 Web 应用程序，并发现它很慢。要了解您的应用程序发生了什么，您需要一些信息。例如，当请求数量很高时，应用程序可能会变慢。如果您有请求计数指标，就可以确定原因并增加服务器数量以处理负载。

组件

Prometheus生态系统由多个协同工作的核心组件构成，共同提供完整的监控解决方案。

1. Prometheus Server（核心服务器）
作为系统核心，负责抓取、存储和处理时序数据。它本身包含三个关键模块：

  • Retrieval（数据抓取模块）： 主动从配置好的监控目标（Target）拉取指标数据。
  • Storage（存储引擎）： 将抓取到的数据持久化存储到内置的时序数据库中，默认保存期限为15天（可调整）。
  • PromQL（查询引擎）： 提供强大的专用查询语言，用于对存储的数据进行实时查询、聚合和分析。

2. Client Libraries（客户端库）
为各种编程语言提供的官方SDK。应用程序集成这些库后，能便捷地内置指标采集功能，并通过HTTP接口将数据暴露给Prometheus Server，是实现应用层自定义监控的主要方式。

3. Exporters（指标导出器）
用于监控那些自身不支持直接提供指标的服务（如操作系统、数据库、硬件等）。Exporters作为代理，收集这些第三方服务的状态数据，并将其转换为Prometheus可识别的格式暴露出来。

4. Push Gateway（推送网关）
作为一个特殊的中转服务，主要用于捕获来自短期任务（如定时批处理作业）的指标数据。这些任务在退出前将数据推送到Pushgateway，随后由Prometheus Server统一拉取，弥补了Pull模型在临时任务监控上的不足。

5. Alertmanager（告警管理器）
独立的告警处理中心。它接收来自Prometheus Server的告警信息，并负责进行去重、分组、静默，以及根据路由规则将告警通知发送到正确的接收渠道（如邮件、钉钉、Slack等）。

6. Service Discovery（服务发现）
支持多种动态发现监控目标的机制（如基于文件、DNS、Consul、Kubernetes等）。在云原生动态环境中，它能自动发现并监控新的服务实例，无需手动修改配置。

7. Grafana（数据可视化）
一个强大的开源可视化工具，常与Prometheus搭配使用。它从Prometheus中查询数据，并提供丰富的图形化仪表盘进行展示，使得监控数据更加直观，同时也支持设置告警通知。

# 指定一个无法登录的系统用户作为启动用户

# 配置 worker 进程数

# 事件配置块

        # 每一个 worker 进程能够同时处理的最大进程数

        # 指定 I/O 模型
        use epoll;
        # 防止惊群效应
        accept_mutex on;
        # 批量分配链接数
        multi_accept on;
}

# HTTP 配置块
http {
        # 指定字符编码
        charset utf-8;
        # 隐藏OpenResty的版本号
        server_tokens off;
        # 定义缓存路径和区域（必须添加这部分）
        proxy_cache_path /var/cache/nginx levels=1:2 keys_zone=static_cache:10m max_size=1g inactive=60m use_temp_path=off;
        # 设置日志格式
        # escape=json 是 NGINX log_format 指令的一个参数，它告诉 NGINX 在生成 JSON 日志时自动转义特殊字符，确保输出的 JSON 格式是有效的、可解析的。
        log_format json_combined escape=json '{"timestamp":"$time_iso8601","remote_addr":"$remote_addr","remote_user":"$remote_user","request":"$request","status":"$status","body_bytes_sent":"$body_bytes_sent","request_time":"$request_time","http_referer":"$http_referer","http_user_agent":"$http_user_agent","http_x_forwarded_for":"$http_x_forwarded_for","server_name":"$server_name","server_protocol":"$server_protocol","upstream_addr":"$upstream_addr","upstream_status":"$upstream_status","upstream_response_time":"$upstream_response_time","upstream_connect_time":"$upstream_connect_time","upstream_header_time":"$upstream_header_time","request_length":"$request_length","request_method":"$request_method","uri":"$uri","query_string":"$query_string","http_host":"$http_host","scheme":"$scheme","gzip_ratio":"$gzip_ratio","connection":"$connection","connection_requests":"$connection_requests","pipe":"$pipe"}';
        # 设置日志的路径
        access_log /var/log/openresty/access.log json_combined;
        # 错误日志
        error_log /var/log/openresty/error.log warn;
        # 启用 gzip 压缩
        gzip on;
        # 压缩级别：1-9，推荐 4-6（平衡性能与压缩率）
        gzip_comp_level 6;
        # 最小压缩文件大小：小于 1k 的文件不压缩（避免压缩开销大于收益）
        gzip_min_length 1k;
        # 压缩缓冲区：4 个 16k 大小的缓冲区
        gzip_buffers 4 16k;
        # 压缩协议版本：支持 HTTP/1.0 及以上
        gzip_http_version 1.0;
        # 对代理请求启用压缩（如反向代理场景）
        gzip_proxied any;
        # 在响应头添加 Vary: Accept-Encoding，帮助代理服务器正确缓存
        gzip_vary on;
        # 指定需要压缩的 MIME 类型（按需添加）
        gzip_types text/css text/xml text/javascript;
        # 载入 OpenResty 能够识别的文件的类型
        include mime.types;
        # OpenResty 无法识别文件类型时，默认的文件类型
        default_type  application/octet-stream;
        # 提升系统文件句柄效率
        sendfile        on;
        # 65秒无请求则关闭连接
        keepalive_timeout 65s;
        # 最多处理1000个请求后关闭连接
        keepalive_requests 1000;
        # 合并数据包发送（适合静态资源）
        tcp_nopush on;
        # 减少交互延迟（适合动态内容）
        tcp_nodelay on;
        # 载入外部的HTTP配置块内部的配置
        include /usr/local/openresty/nginx/conf/conf.d/*.conf;
}

EOF

prometheus 配置详解

Prometheus 的配置详解主要围绕其核心配置文件 prometheus.yml 展开，该文件通过定义全局设置、抓取目标、数据存储规则和告警管理等关键部分，完整地构建了监控体系的运作逻辑。其中，全局区块（global）设定了数据抓取间隔等基础参数，抓取配置区块（scrape_configs）则具体指明了从哪些监控目标（如服务器节点、应用程序接口）拉取指标数据，并可通过标签（labels）对数据进行灵活标记与分类。此外，配置还涉及数据存储路径与保留策略的设定，以及如何与 Alertmanager 联动实现告警规则的触发与通知，从而形成一个从数据采集、存储、查询到告警的端到端监控解决方案。

global 全局配置

Prometheus 的 global 全局配置定义了整个 Prometheus 实例的默认行为，为数据采集、规则评估等核心活动提供了基础设定。下面这个表格汇总了 global 段中常见的配置项及其作用：

配置参数 功能说明 默认值
scrape_interval 抓取目标指标数据的默认频率 1m
scrape_timeout 每次指标抓取请求的超时时间 10s
evaluation_interval 评估告警规则 (rule_files) 的频率 1m
external_labels 与外部系统通信时添加的标签（Prometheus主从） 无
  • 若想不重启Prometheus就加载配置，需确保启动参数包含 --web.enable-lifecycle，然后通过 curl -X POST http://localhost:9090/-/reload 触发热加载
  • 建议在重载配置前使用 promtool check config prometheus.yml 命令验证配置文件语法，避免因配置错误导致服务异常。

alert_relabel_configs:
  - source_labels: [dc]        # 从现有标签 'dc' 取值
    regex: "(.+)\\d+"          # 正则表达式：匹配 "文字+数字" 的模式
    target_label: dc1          # 将处理结果保存到新标签 'dc1'

工作示例

假设有一个告警带有标签 dc="beijing1"：

  1. 提取源标签：从 dc 标签获取值 "beijing1"
  2. 正则匹配：
    • 正则表达式 (.+)\\d+ 分解：
      • (.+)：捕获组，匹配一个或多个任意字符
      • \\d+：匹配一个或多个数字
    • 对 "beijing1" 的匹配结果：
      • 整个字符串匹配成功
      • 捕获组 (.+) 捕获到 "beijing"
  3. 替换操作：
    • 默认动作为 replace，将捕获组的内容赋给目标标签
    • 新标签：dc1="beijing"

效果：去掉了数据中心编号，只保留地区名称。

rule_files 规则文件（告警规则）

这段内容主要介绍了告警规则的配置。其核心作用是定义基于哪些指标来触发报警（类似于触发器机制）。规则设定完成后，Prometheus 会根据全局配置中的 evaluation_interval 参数定期扫描并加载这些规则；当规则发生变更时，系统也会自动完成加载。

至于报警信息的传递方式和路由分配，则由 Alertmanager 插件负责实现。

2
3

# Load rules once and periodically evaluate them according to the global 'evaluation_interval'.
rule_files:
   - "/usr/local/prometheus/rules/*.yaml"

# 告警组 对一组相关的告警进行统一定义，下面可定义多个告警规则
groups:
- name: test-rules
  rules:
    - alert: InstanceDown # 告警规则的名称
      expr: up{job="prometheus"} == 0 # 告警的判定条件，参考PromQL高级查询来设定
      for: 10s # 满足告警条件持续时间多久后，才会发送告警
      labels: #标签项
        severity: error
      annotations: # 解析项，详细解释告警信息;在告警产生时会一同作为参数发送到alertmanager
        summary: "{{$labels.instance}}: has been down,is {{$value}}"  #摘要
        description: "{{$labels.instance}}: job {{$labels.job}} has been down "  #描述

scrape_configs

scrape_configs 是 Prometheus 配置的核心部分，用于定义抓取目标和抓取行为。

scrape_configs:
  # 抓取 Prometheus 自身指标
  - job_name: 'prometheus'
    static_configs:
      - targets: ['localhost:9090']
  
  # 抓取 Node Exporter 指标
  - job_name: 'node-exporter'
    static_configs:
      - targets: ['node-exporter:9100']

job_name ：定义抓取任务的名称，会作为 job 标签附加到所有抓取的指标上。

scrape_interval ：抓取间隔，覆盖全局的 scrape_interval。

scrape_timeout：抓取超时时间。

metrics_path：指标路径，默认为 /metrics
